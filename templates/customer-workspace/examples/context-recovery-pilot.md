# Cold-session pilot

Adopt the project's actual rules and select an authorized bounded assignment. Do not use
fictional issue numbers, sources or approvals as evidence in a real project.

1. Session A reads the assignment and relevant shared context, performs a bounded step
   and saves the current handoff at the designated planning home.
2. Preserve the actual code/check revisions, open questions, unsaved work and pending writes.
3. Introduce an authorized relevant source change, or observe one that occurs naturally.
4. Start a fresh Session B with only the assignment and shared-source entry. Do not provide
   the old chat, expected diagnosis or intended answer.
5. Observe its source selection, applicable decisions, treatment of changed scope/approval,
   preservation of human feedback, next action and actual verification.
6. Have a person check the result and record evidence, errors, recovery time and limits.

Also exercise an inaccessible designated tracker and a clear small edit. The first must
not create a mirror plan or invent current state; the second must not add unnecessary
process records. Further integration cases include timeout after write, competing workers,
tracker outage, stale test evidence and duplicate/cancelled closure.

Report scenarios as not run, passed, failed or blocked. File snapshots exercise source
reasoning but do not prove live API access, atomic claims or installed OpenCode/Claude
behavior. Local validators check structure only. Keep each observation's model/host,
process revision, artifacts and limitations so another evaluator can repeat the case.

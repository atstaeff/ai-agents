# Catalog restructure: bounded forward observations

Date: 2026-10-22. These synthetic cases examine selected procedures after the catalog
restructure. They are observations from three fresh agent sessions, not a benchmark,
independent human approval or evidence of staffing savings. The runtime inherited its
host model; the model/version was not pinned. No live tracker or installed-host test
was performed. Outputs were inspected by the integrating agent.

## Cases and observed behavior

| Case | Supplied facts and task | Observed result |
| --- | --- | --- |
| Architecture | Five-person team; API and SQL; accepted customer-scoped attempt identity; proposed global payload-digest lookup and Kafka/four services; two author-reported tests. Review with architecture-planning. | Identified cross-customer existence/reference disclosure and the conflict with the accepted decision. Distinguished unverified retrieval access from demonstrated disclosure. Challenged the unsupported service split and requested boundary, concurrency and recovery evidence. Did not claim approval or tests actually run. |
| Delivery | Jira owns PORTAL-17; only an old snapshot is accessible; seven-day retry semantics unresolved; two contributors and one reviewer. Propose an increment using project-management. | Marked current priority/status unverified; assigned semantic decisions to the Product Owner; proposed a measurement method without inventing a baseline; limited review work to reviewer capacity. No tracker writes or duplicate plan files. |
| Small edit | A README heading says `Servcie overview`; request a correction using work-management. | The only file remained README.md, with `Service overview` and the unchanged body. No work record or additional process documents were created. |

The cases used isolated local directories. The architecture agent received the current
skill and its linked canonical references; it wrote only its review in the fixture.
The delivery response remained conversational and read-only. The small edit had write
scope only to its example directory. None had authorization for external actions or
further delegation. No private customer data was used.

## What this supports and leaves open

These observations support retaining the added decision-authority, quality-evidence,
capacity and small-task guidance. They do not isolate the causal contribution of each
instruction, measure repeated-run reliability, or prove real customer adoption. Re-run
representative assignments when model, host, catalog behavior or project context changes.

Automated repository checks separately cover domain discovery, duplicate rejection,
bundled Markdown exclusion, stable native export names, API metadata and generated
website inclusion. The local workflow replay exercises actual loopback HTTP, feedback,
stale-write rejection, native export protection and recovery from a saved work record.
Those checks validate tooling behavior, not reasoning quality or business outcomes.

# Shared working contract

Read this for process uncertainty; routine sessions start with [session rules](SESSION-RULES.md).

Follow the current user and host instructions, then project rules. Use English for
shared repository artifacts and the user's language in conversation. Load only relevant
sources and selected skills; do not scan the entire catalog for a routine task.

## Understand and plan

Read `AGENTS.md`, the request and affected code, tests and decisions. Use the existing
issue for team scope/acceptance and the PR for implementation and evidence. Do not create
an issue or process file automatically for a direct request.

Small clear changes need no separate plan. For larger personal work, use the user's
configured Second Brain project folder and [work template](../templates/delivery/personal-plan.md)
when useful. Resolve private filesystem paths and the exact Obsidian vault name from
user-local instructions, never public project configuration. Follow customer policy on
external storage. Reuse the current plan; do not mirror its task list into shared systems.
If the vault is unavailable, say the plan is not saved and keep a short session plan;
continue independent authorized implementation. Never claim persistence or synchronization.

Keep a plan to the goal, acceptance, next steps, checks and current resume point. Output
an encoded Obsidian URI after saving; [Obsidian guidance](../skills/knowledge/obsidian-para/SKILL.md)
explains Windows/WSL paths and the custom-link limitation in some chat UIs.
If the project explicitly requires a shared execution plan, use that designated home.

## Implement and verify

Resolve routine reversible choices independently. Obtain the accountable owner's decision
only when a consequential ambiguity blocks work or existing policy requires approval.
For required plan review, present the current concrete revision, preserve actual feedback
and approval, and reopen review only for material scope/design changes. An unavailable
review tool is not approval. See [optional plan review](PLAN-REVIEW.md).

Use [Herdr](HERDR.md) when available and usable. Check existing sessions, select actual
model/effort routes, organize labelled tabs and isolated writers, and fill available
capacity with independent ready work. Use native commands for mechanical dispatch;
reserve strong/high reasoning for complex judgment and consequential review. Report
a concrete readiness gap before using an available fallback.

Use the existing stack and the smallest complete increment. Delegate only when the host
supports and authorizes it and coordination is useful. Give each writer a bounded scope;
inspect returned work and verify the integrated result.

Run the project's applicable checks. Exercise affected user/API behavior and important
failure cases, not only compilation. Preserve human edits and comments; reread before
writes and use available version checks. After a remote timeout, inspect existing effects
before retrying. State actual results, unrun checks and material limits.

## Preserve the result

Update shared documentation to match the implemented behavior. Put significant decisions
at the project's ADR home with context, alternatives, choice, consequences and evidence.
Draft a decision when it arises; finalize it against actual implementation and authorized
acceptance. Do not silently replace an accepted decision or create an ADR for every edit.
Keep private plans, transcripts, vault paths and secrets out of public artifacts.

Update the personal plan with progress or mark it complete. Report changed behavior,
verification and remaining limits in the PR/current request. No mandatory iteration report,
agent handoff or knowledge page is needed for every task. Merge, publication, messages and
deployment follow existing authorization; a plan is not permission for them.

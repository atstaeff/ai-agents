    Project workspace: the shared memory for people and AI¶

    For a short explanation you can share with a team and a practical first setup, start with Adopt the workspace. Use the project setup prompt to configure an existing project. This page remains the detailed contract behind those entry points.

    Use workspace/ as the project's shared working context. It holds the tooling map, entry points, decision rationale and current knowledge, plus optional local work records. People and AI use the same sources. Another person or a fresh session must be able to continue an assignment without the previous conversation.

    This concept combines the operating model, working contract, configuration and recovery contract. These documents provide focused operational instructions; this page explains how their parts fit together.

    1. Outcomes and principles¶

    • Preserve why a significant choice was made, including alternatives and consequences.
    • Keep one authoritative home for each fact and one live plan per assignment.
    • Load relevant context from shared sources instead of growing a mandatory chat history.
    • Make AI a sparring partner: inspect assumptions, propose alternatives and identify evidence that could change the recommendation. Work within the assigned decision rights.
    • Keep customer knowledge with the customer and general expertise in the agent catalog.
    • Scale ceremony to uncertainty and consequence. A clear small correction stays direct.

    The workspace is a team convention, not a model memory API or a new project-management system. Existing customer methods remain valid, including their own planning process, Plan/Build/Review or another adopted method. Use an existing equivalent entry point when the project already has one.

    2. Folder and information ownership¶

    All paths below are relative to the project root. Create only the parts the project needs.

    Path Purpose Update and publication rule
    AGENTS.md Entry instructions, commands and pointer to workspace config Preserve project rules; keep short
    workspace/README.md Outcome, scope and links to authoritative sources Reviewed project context
    workspace/workspace.yml Machine-readable tool and process mapping One configuration; no credentials
    workspace/working-agreement.md Authority, review, flow and completion policy Adopt with the responsible owner
    workspace/stakeholders.md Decision roles and permitted communication Use verified contacts within scope
    workspace/decisions/ Significant ADRs and their historical rationale Preserve accepted reasoning and replacement links
    workspace/knowledge/ Current domain, architecture and operational knowledge Update affected pages when behavior changes
    workspace/iterations/ Outcomes, learning and open follow-up Link evidence; no duplicate live task list
    workspace/work/ Optional local record for an otherwise unassigned larger outcome Local and ignored by default
    workspace/archive/ Completed local work records Local history, excluded from routine context
    workspace/generated/ Replaceable previews and derived output Ignored; never a source of truth
    workspace/exports/ Optional generated host bundles Ignored; edit canonical catalog sources

    The --workspace CLI option still means the project root. For a project at /path/to/project, pass that root; the store writes workspace/work/ beneath it. Passing /path/to/project/workspace would create an unintended nested workspace.

    The local store uses this conventional folder name. A customer can retain a different knowledge directory through the declared locations, but the store does not provide a configurable alternate record root. Resolve an existing conflicting workspace/ before using local records; adopting documentation never authorizes overwriting customer files.

    3. One plan, even with several tools¶

    Project arrangement Live assignment and plan Code and proof Durable knowledge
    GitHub Assigned issue; Projects owns adopted board fields Repository, PR and checks Project-selected repository or wiki
    Jira with GitHub Jira ticket; no mirror GitHub issue Linked GitHub PR and checks Repository ADRs and/or Confluence
    Split product and engineering planning Jira owns product/capacity; explicitly scoped engineering items own technical increments Linked repository changes per increment Shared customer-owned sources
    Larger local request with no assigned tracker One workspace/work/<slug>.md Local changes and actual checks Existing project documentation

    For split planning, use a stable delivery-object reference and explicit parent/child relationships. Define ownership per field and work item before writing. Do not maintain two editable copies of the same live plan. A missing connector does not change ownership. Prepare an unsent proposed update and continue only independent authorized work.

    4. The YAML contract¶

    Use the GitHub example, Jira example or this repository's configuration. All use the same JSON Schema and validator.

    Required version-1 fields retain the six authoritative locations, project name and working-agreement/stakeholder pointers. Optional sections add:

    • profile and method: project arrangement and chosen delivery method.
    • repositories: named code repositories, optional local paths and base branches.
    • planning: separate priority, iteration and engineering-status ownership when needed.
    • flow: actual board-state mapping, blocked property and completion policy.
    • handoff: the existing work-item section and a shared template.
    • labels and reviewers: adopted coordination labels and responsible reviewers.
    • commands and quality_gates: reproducible project commands and required checks.
    • actions: agreed action categories, still subject to real authorization and permissions.

    The YAML is declarative. Validation makes no connection, creates no board or labels, executes no commands and grants no authority. Confirm actual access and adopted policy in the chosen host. Do not invent GitHub Project IDs, Jira fields or reviewer approval. Relative paths resolve from the project root, not from the configuration directory.

    The older standalone v0.2 concept example used schema_version, sources and paths; it was explicitly a separate example schema. Map those ownership values into this contract rather than copying its YAML verbatim. Existing toolkit version-1 configs remain valid without the new optional sections. An explicitly linked project.yaml is supported; keeping it beside workspace.yml is rejected as ambiguous.

    5. Initial project setup¶

    1. Determine the outcome, scope, quality constraints and accountable people.
    2. Inspect the existing tracker, repositories, instructions, contracts and decisions.
    3. Adopt the minimum entry pages and map actual locations in the YAML. Preserve existing policies and private content; do not copy fictional customer details into production.
    4. Agree which actions are allowed within an assignment, which require a decision and which tools or credentials the host actually has.
    5. Record significant initial choices and unresolved assumptions. Architecture evolves during delivery; do not invent historical decisions or require all design up front.
    6. Validate the config and perform the host smoke check.
    7. Select one bounded real assignment and run the manual flow before adding orchestration.

    6. Delivery and sparring¶

    Start from an outcome and observable criteria. Inspect relevant constraints before proposing the smallest complete increment. When uncertainty matters, compare alternatives, state the recommendation and tradeoffs, and name what evidence would change it.

    Follow the project's review policy. Routine reversible implementation details within the assigned scope can proceed. An incompatible API change, changed data meaning, material cost/security consequence or disputed architectural constraint needs the accountable role. Do not ask for every routine step or silently reinterpret consequential requirements.

    Implement, exercise the affected behavior and link criteria to actual results on a specific revision. A second AI review is not automatically independent approval. Update affected knowledge and significant decisions as they arise. The iteration report links these outcomes and unresolved items; it is not the first place to reconstruct rationale.

    Trigger Action Result
    New assignment or resumed session Read current sources and choose a bounded increment Current scope and next step
    Required decision or plan review Obtain the accountable owner's decision on the current revision Preserved decision or approval evidence
    Authorized increment Implement and verify criteria; save evidence and handoff Reviewable result on a known revision
    Changes requested Revise the affected increment and repeat relevant checks Updated result and feedback disposition
    Acceptance at the completion point Close work and link reusable learning Verified outcome, with impact still separately measured

    7. Decisions, current knowledge and recovery memory¶

    Question Read or update
    Why did we choose this approach? ADR with context, alternatives, evidence, decision and consequences
    What currently applies? Accepted decisions in scope and current contracts
    What is actually implemented? Code, tests and operational evidence
    What are we trying to change? Current assignment, criteria and human feedback
    Where do we continue? Bounded handoff in the existing planning home

    Use stable ADR IDs and explicit statuses. A proposed replacement cannot revoke an accepted decision. A substantive replacement gets a new ADR, a supersedes relation and an updated old status; preserve the old reasoning. Correct factual metadata without silently rewriting accepted rationale. Resolve contradictions by scope and authority, not by the newest file timestamp or the current code alone.

    Record useful outcomes and reasons, not private reasoning traces or full chat dumps. The workspace supports shared project memory; it does not make model-internal memory reliable or replace the authoritative sources.

    8. Context loading and fresh sessions¶

    Load the short entry, config, applicable rules and actual assignment first. Follow links to affected code, tests, contracts and decisions. Search the bounded project when a relevant source is missing; an absent link does not prove that no decision exists. Load full documents only as needed. Do not load the entire archive or every agent/skill.

    Before resuming, compare the current sources with the last handoff: assignment revision, relevant commits, ADR status, current approval and tested criteria. Refresh affected context after material changes. An unrelated commit does not require rereading everything. Do not omit relevant constraints merely to satisfy an arbitrary token budget.

    Save the bounded handoff after material increments and before a known pause or session/model switch. Include unsaved work and pending external writes. One current summary belongs inside the assigned work item or existing local record; the template file is not another running plan.

    9. Flow, completion and failure recovery¶

    Map Todo, In Progress, In Review and Done to the adopted board. Blocked is an additional property with reason, owner and resume condition; preserve underlying flow position and WIP. A team's existing equivalent mapping may differ when explicit.

    For code, Engineering Done requires criterion evidence, required review and authorized integration at the agreed completion point. Acceptance, merge, deployment and measured impact remain distinct facts. Cancelled, duplicate and not-implemented closures do not count as delivered. An investigation can finish with a verified answer.

    After a timeout, inspect the original system for the intended write before retrying. Git, trackers and review systems are not one atomic transaction. Reconcile partial effects and preserve intervening human edits. One writer owns an assignment or separate bounded scope. Multiple workers need an effective shared claim and recovery policy; an assignee field alone is not an atomic lock. Record each relevant repo revision and integration order for multi-repository work.

    The toolkit implements local record persistence, stale-write protection and exports. It does not implement tracker polling, cross-system transactions, distributed claims or an agent/session runner. The runner example describes an integration contract rather than an installed service.

    10. Publication and privacy¶

    One directory can hold several information types without granting them the same audience. Local work/, archive/, generated/ and exports/ are ignored by default and excluded from the example knowledge graph and Docusaurus publication. Git ignore rules alone do not stop a website from reading files on disk.

    The Docusaurus fragment publishes named root entry pages and the selected knowledge, decisions and iteration directories. Review that allowlist and sources before adopting it. Do not add local work directories to the site. Configuring workspace/ as a broad content source without exclusions would publish local notes. Keep secrets and personal material outside public repositories, and enforce the customer's access requirements on the published site.

    docs/ remains generated Pages output in this repository. Its MkDocs site reads explicit canonical sources through the docs hook; it does not recursively publish the root workspace. The export manifest .ai-toolkit-manifest.json remains an adapter-ownership file so existing bundles retain protection against overwriting human edits. It is not a project-memory folder.

    11. Moving existing local work¶

    Stop agents, dashboards and editors that write records. Back up the project. Then run:

    python3 tools/ai_toolkit.py work --workspace /path/to/project migrate --dry-run
python3 tools/ai_toolkit.py work --workspace /path/to/project migrate
python3 tools/ai_toolkit.py work --workspace /path/to/project list

    Migration moves .ai/work/ and .ai/archive/ into workspace/ without changing file contents. It checks both destinations before moving anything, refuses existing target directories and rejects symlinks. It does not merge conflicts, rewrite relative links, move unknown .ai content or grant permission to disclose records. Resolve conflicts and update affected links deliberately. The empty old parent directory is removed; remaining unknown content is preserved and reported by legacy_directory_remaining.

    Each directory move is a separate filesystem operation. If interrupted, inspect both locations and rerun after stopping writers; already-moved directories are left alone. This is not a distributed migration lock. The store reports remaining legacy records instead of hiding them or creating a second plan. Old ignored paths stay ignored during transition. Regenerate disposable previews and bundles under the new paths, then update host references deliberately; never delete edited bundles as part of a blind migration.

    12. Evidence and adoption decision¶

    Run the cold-session pilot on real authorized work. Test a relevant decision change, unavailable tracker and small bypass task. Separately exercise installed-host discovery, effective permissions, live API retries and competing writers before expanding autonomy.

    The local observation records bounded recovery behavior, not broad productivity or installed-host reliability. Compare a few similar assignments for reconstruction effort, recovery errors, time to accepted outcome, review/rework and intended user impact. State model/host and process versions, raw evidence, failed attempts and unrun boundaries. Keep rules whose benefit exceeds their maintenance cost; improve repeatable tooling instead of continually enlarging prompts.

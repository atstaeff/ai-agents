Start with one real assignment

Adopt the project entry, choose a host and complete one bounded outcome before adding more roles or tools. The catalog works with your existing stack and delivery systems.

1. Establish the project sources​

Merge the starter into the repository's existing root instructions:

  • AGENTS.md identifies collaboration rules and authoritative sources.
  • PROJECT.md describes goals, scope, stakeholders and ownership.
  • CONTRIBUTING.md describes the process, tools, checks and action boundaries.

Link existing equivalent pages where they already own these facts. Fill in real issue, review, knowledge and decision locations. No YAML file or workspace/ tree is required. The adoption guide covers existing repositories and central web policy.

2. Choose the runtime and a bounded catalog​

Follow runtime exports for Herd, OpenCode, Copilot, Claude Code or portable profiles. That guide owns current commands, layouts and options. Use a dedicated export destination, preserve existing host instructions and verify discovery and effective permissions with the host check.

Use Herdr whenever installed and usable; reuse the matching project session and organize labelled lead/specialist tabs. Complex judgment uses strong/high reasoning, bounded execution uses economical models and mechanical coordination uses native tools. Scale parallel work to actual resource, provider, budget and review capacity. Report a concrete gap when falling back.

Start with a small preset or explicitly selected profiles. Configure providers, credentials and model choices in the host. For a coordinated assignment, choose the relevant product, architecture or delivery leader and bounded specialists; see orchestration.

3. Run one useful outcome​

TeamFirst assignmentEvidence to retain
EngineeringFix a reproducible defect or deliver a small feature in the existing stackBehavior checks, review findings and the linked change
ProductResolve one uncertain user problem or prioritize a bounded experimentSource observations, assumptions, acceptance and the next decision
PlatformImprove a deployment, service boundary or operational recovery pathThe changed contract, a representative check and recovery evidence

Use the designated issue or ticket for shared scope, acceptance and evidence links. For code changes, keep implementation and review details in the linked PR. For an outcome without a code change, retain its result and review at the assignment and linked knowledge source. Personal working plans stay private; if configured storage is unavailable, mark the session plan as unsaved. A small clear correction needs no plan file.

Run the project's actual checks, update affected knowledge and preserve significant decisions. Try resuming from the shared sources in a fresh session. Report what was verified and what remains unknown before expanding concurrency.

The working contract defines the process. Add the optional local workbench or integrations only for a concrete need.

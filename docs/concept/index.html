Work with AI as a teammate

Run a project with one clear outcome, one current assignment and a small shared memory. Use AI to explore, plan, build, verify and maintain that memory within actual permissions. People own priorities, consequential decisions and acceptance. This is a practical default built from established practices, not a claim of universally optimal productivity.

Start with AGENTS.md and authoritative project sources​

Use AGENTS.md as the collaboration entry. It names where to read vision, goals, stakeholders, scope, process, work, current knowledge and decisions, and defines ownership, parallel-work, verification and handoff rules. Read the worked example and adapt the team starter or another instruction template.

EntryMaintain here
AGENTS.mdSource navigation and the collaboration contract
PROJECT.md or equivalentVision/goals, affected groups, decision roles, scope and source map
CONTRIBUTING.md or adopted central processWorkflow, actual tools/commands, relevant skills and quality gates
Project-owned knowledge and decisionsCurrent behavior and preserved significant rationale

Sources can be local Markdown or accessible web documentation. Read the explicitly adopted process, pin shared policy to a verified source revision or maintained version and record what was loaded. Keep each fact at its authoritative source. No YAML manifest or workspace folder is required. Verify instruction discovery and remote retrieval in the chosen host.

Docusaurus publishes the same selected Markdown as a reading view. Project facts stay with the project; the central engineering site owns reusable methods and templates. See the project concept for versioning, unavailable-source handling, publication boundaries and compatibility with existing tools.

An expertise catalog supplies reusable skills. Project facts stay in the project. Load the narrowest useful skill; another profile need not mean another session.

Run one delivery loop​

Clarify → Plan → Build → Verify → Integrate and retain useful knowledge. These activities can happen in one conversation and issue. They require no phase documents.

ActivitySmallest useful result
ClarifyWho needs what outcome, boundaries and observable acceptance
PlanNext complete increment, important uncertainty and affected sources
BuildFocused implementation using the existing stack
VerifyActual criterion-linked checks, relevant failure cases and practical limits
Integrate and retainRequired acceptance/integration, current knowledge and durable rationale

For a clear reversible correction, inspect, change and check directly. For an ordinary feature, use the compact assignment inside the existing issue. For an uncertain or consequential change, add a concept/spec and the necessary decisions. Each artifact must resolve an uncertainty or preserve useful knowledge.

Use Todo, In Progress, In Review and Done, or the project's equivalent. Track blocked work with its reason, owner and resume condition; keep its flow position visible. Cancelled, duplicate and declined work are not delivered. Engineering Done means the agreed evidence, required review and authorized integration at the project's completion point. A draft PR, passing tests, deployment and measured user benefit are distinct states.

Control the project without a second management system​

Choose one person accountable for priority and acceptance, plus a technical decision owner when needed; one person can hold both roles. Select the next increment by value, risk, dependencies and review capacity. Default to one active increment per accountable owner; expand only when the team can integrate and review the additional work.

Keep priority, assignment, plan, feedback and progress at their designated work home. Use a few tasks only when coordination needs them. On material progress or a blocker, update the same assignment. At a useful review point, link delivered outcomes, unresolved risks and the next choice there; a separate iteration report or recurring meeting is optional.

For each assignment, identify the accountable human, active writer, bounded change scope, dependencies, required reviewer and integration owner. One person can hold several roles. Use independent branches and working directories for parallel writers. Agree changes to shared contracts before dependent implementation. Coordinate overlapping scopes through an effective shared claim and recovery mechanism; without it, serialize overlapping writes. An assignee or Git branch is not a distributed lock.

Select specialists for bounded uncertainties through supported authorized host capabilities. Keep integration order visible, integrate reviewable increments frequently within actual permissions, and verify the combined result. For several repositories, record a tested revision per repository and cross-repository acceptance. See the collaboration templates. This toolkit implements no distributed lock, tracker synchronization or model orchestration.

Keep a small, connected memory​

Create only the records needed by actual work. The project entry links the current ones.

RecordCreate whenAfter the work
IdeaAn opportunity needs capturingMark selected, deferred, declined or delivered; link its result
Concept/specA meaningful uncertainty or contract needs explanationKeep the designated living contract current; otherwise mark it historical and link its current successor
DecisionA significant choice's reasons will matter laterPreserve accepted rationale and replacement links
Current knowledgeReusable behavior or operating knowledge would otherwise be lostUpdate from verified implementation; show intended/partial states
Incident reviewImpact, recurrence or uncertainty warrants learningPreserve facts and link owned follow-up issues and knowledge changes

An idea is not a commitment. An agreed concept is not evidence of delivery. Code changes do not revoke accepted decisions. AEK makes rationale compact: starting situation, insight from alternatives/evidence, and consequences of the chosen response.

Working plans and tasks remain with the completed assignment as history. Before replacing or deleting a derived plan, preserve its still-important decisions. Remove disposable generated output and genuine duplicates deliberately. Archive means searchable history outside routine context; it does not mean losing the reasons. See the knowledge lifecycle and recovery rules.

Resume from current sources​

A new session reads the current assignment, project entry and affected knowledge, contracts and decisions, then compares the last bounded handoff with current revisions. Search the affected project if links are missing. Load historical plans only to answer a specific question; never require the entire chat, catalog or every ADR.

Before interruption, save the current result, relevant revisions, actual check evidence, blocker/decision owner, pending writes and one next action in the existing assignment. An optional host/session link aids navigation; shared knowledge must remain usable without it. Use the recovery contract for conflicts and incomplete writes.

Let each project choose its tools​

Jira can own the assignment and GitHub the code review. Do not create a mirror issue, local work record or CSV task list. With no designated system, use one work record. If an authoritative system is unavailable, report the gap and prepare an unsent update; continue independent authorized work without silently changing the work home.

Use lean Plan/Build/Verify by default. For larger requirements, a project may choose Spec-Driven Development; BMAD can support discovery, planning and delivery. Keep their required artifacts at their existing homes, link them here and state which source owns requirements versus status. Select one primary delivery method per assignment. Choosing a delivery method installs nothing. Never reconcile intent by merely accepting whatever code happened to be produced. See the method selection and retention guide.

Add rigor where it earns its cost​

Make the relevant qualities measurable using the quality standard. For significant changes, cover affected consumer contracts, security/privacy boundaries, recovery and maintenance cost. Prefer understandable boundaries; new infrastructure, frameworks and abstractions need evidence of benefit.

Plan review is required when the user or project requires it. Preserve the actual approval of that revision before dependent work. Material changes reassess affected approvals and checks. Merge, deployment, messages and destructive actions follow their actual scope; a role label, template or YAML file grants no authorization.

Start with the lean worked example. For more elaborate customer coordination, use the worked assignment and the detailed project concept. Observe reconstruction effort, rework, review time and useful outcomes on real assignments before adding automation.

Practices behind this default include DORA small batches, short decision records and SRE incident learning. Their combination here is a project convention; its benefit still needs observation in the adopted project.

Engineering collaboration contract

This repository maintains an English engineering agent/skill catalog, a shared operating model and a local Python toolkit. Follow current user and host instructions and the applicable project rules. Use the user's language in conversation.

Project sources​

Read these entry sources, then only the detail relevant to the assignment:

NeedAuthoritative source
Vision, goals and success signalsProject
Stakeholders and decision/acceptance rolesStakeholders
Scope, exclusions and constraintsScope
Process, tools, skills and checksContributing source, published process
Current knowledge and significant decisionsKnowledge index
Acceptance and action boundariesWorking agreement
Assignment and acceptanceThe current request or its existing shared issue/PR
Personal execution planThe user's private Second Brain, when available

The documentation website publishes the maintained sources. This checkout is authoritative for its revision; the published site can lag an unmerged change. Read the project concept when changing the operating model, information ownership, knowledge layout or documentation publication. No project.yaml or workspace folder is required to adopt this contract.

Ownership and parallel work​

Keep one authoritative shared work item per assignment. Personal plans stay private and are not required for teammates. Identify the accountable human owner, active writer, bounded change scope, dependencies and integration owner. Use separate branches and working directories for independent writers; agree changes to shared contracts before dependent implementation. Coordinate overlapping scopes through the project's shared claim/handover mechanism; an assignee or a branch is no atomic lock. Preserve other contributors' changes and reread shared records before updating them.

Follow the shared workflow and recovery contract. Proceed with routine reversible choices within the assignment; resolve consequential scope/design conflicts with the named owner. Delegate only when supported, authorized and useful. Put shared scope, acceptance, feedback and review evidence at the work home; record durable rationale in knowledge.

Repository navigation and engineering rules​

  • Maintain canonical profiles in agents//.agent.md and skills///SKILL.md. Use catalog domains and catalog guidance. Keep exported names unique and name/description frontmatter present.
  • Read the selected skill body and relevant references; links neither install skills nor start sessions. Keep host-specific discovery and permissions in adapters; see portability.
  • Preserve Python 3.11+ and the standard-library-only core. Keep the dashboard on loopback, its assets local, and its comment persistence and stale-write protections intact.
  • Edit canonical sources. website/ owns Docusaurus; docs/ is generated GitHub Pages output. Preserve public routes. Keep private data, local work and generated bundles out of commits.

Verification and completion​

Use the runbook and CI. Run checks appropriate to the change:

python3 tools/ai_toolkit.py check
python3 -m unittest discover -s tests -v
uv run --locked --group validation python -m unittest discover -s tests -v
npm --prefix website ci
npm --prefix website run build

Verify combined changes after integration and associate evidence with the tested revision. Report passed, failed, blocked and unrun checks honestly. Required review, acceptance, integration and deployment are separate states. Do not merge or deploy without an explicit request.

Shared memory and handoff​

Maintain affected current knowledge and record significant rationale at knowledge/. Preserve accepted reasons and replacement links. Before pausing, save result, relevant revisions, evidence/limits, blockers, pending writes and one next action at the existing work home. A fresh session checks current sources. For otherwise unassigned larger local work, the optional toolkit uses ignored workspace/work/ and workspace/archive/; those are storage details, not the project model.

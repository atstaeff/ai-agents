# Repository Contribution

1. Read applicable agent instructions and root `project.yaml`, then its declared
   context, owner and contribution references. For legacy projects, follow the
   explicitly declared equivalent entry and configuration. Locate the vision, current goal,
   scope boundaries, decision owners and required working process. Follow current
   instructions and local policy; do not replace them with a generic catalog workflow.
2. Read root `project.yaml` (or the explicitly declared legacy configuration). Resolve
   work, review, knowledge and decision homes from that map.
   Inspect actual setup/check commands, affected source and CI. Locate existing work
   before creating records. Keep project facts at their source, not in this skill.
3. Select only the expertise needed for the assignment. Use
   [product-discovery](../product-discovery/SKILL.md) for uncertain value/scope,
   [work-management](../work-management/SKILL.md) for a larger assignment,
   relevant engineering/language guidance for implementation, and
   [testing](../../quality/testing/SKILL.md) and [pr-crafting](../pr-crafting/SKILL.md)
   for verification and review. Reuse guidance already loaded; avoid recursive
   onboarding, a full catalog scan or a new session for every skill.
4. Match configured information ownership to available host integrations. Inspect the
   actual tool contract, source revision and effective permissions before writing.
   If access is missing, name the blocked operation and prepare an unsent update;
   continue independent authorized work without inventing tool access or a mirror plan.
5. Implement the smallest complete authorized change in the existing stack. For a
   clear small correction, inspect, edit and check directly. Otherwise keep acceptance,
   plan and feedback at the existing work home. Respect required plan review, preserve
   human edits and resolve consequential conflicts with the responsible owner.
6. Run relevant project checks and inspect the final diff. Report actual evidence and
   limitations; distinguish verification, acceptance, merge and deployment. Update
   affected current knowledge, retain significant rationale and leave a bounded handoff
   in the same assignment before interruption. Perform external actions only within
   actual authorization.

## Output

Produce the reviewable change and a compact result: addressed outcome, relevant checks,
remaining gaps and next action. Link the authoritative sources when useful; create no
separate onboarding report, process file or project skeleton by default.

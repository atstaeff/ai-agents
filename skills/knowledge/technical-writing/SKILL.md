# Technical Writing

## Workflow

1. Identify the reader, task/decision and canonical publication home. Read the existing structure, terminology and source ownership rules; update the owner source before generated views. A small correction needs only its affected context.
2. Verify claims against current code, contracts, decisions or official references. Distinguish intended, implemented and observed behavior; mark unresolved facts rather than inventing support, approval or measured benefits.
3. Choose the useful shape: a task guide with prerequisites and expected results, a runbook with signals and recovery, an explanation with reasons/tradeoffs, or exact reference data. Use the existing format; create no duplicate guide by default.
4. Write a complete reader path with concrete steps, meaningful examples and failure recovery. Keep commands compatible with the supported environment; make placeholders obvious and keep secrets/private paths out. Link shared rules and facts at their owner instead of copying them.
5. Edit for accurate meaning, consistent terms, short sections and clear headings. Remove repetition without dropping governing constraints. Preserve stable links/anchors or provide the project's migration path; separate editorial changes from consequential policy/behavior proposals.
6. Verify changed relative links and available documentation/render checks. Replay safe example commands or the reader journey where practical; label unrun and environment-dependent steps. Ensure generated publication reflects the canonical revision when generation is in scope.

## Result

Deliver the revised source, checked reader path/links/build and material fact or execution
gaps. Policy owners decide changed meaning; publication and messages follow existing
authorization. Do not claim an independent review or successful replay that did not occur.
